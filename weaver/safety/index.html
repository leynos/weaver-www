Security Architecture

The Double-Lock
Mechanism

Weaver assumes that AI agents, while powerful, are fundamentally untrusted actors within the local environment. Our security model enforces strict containment through a dual-layer strategy: the Birdcage sandbox and the Policy gatekeeper.

Layer 1: The Birdcage

The Birdcage is a kernel-level sandbox powered by seccomp-bpf and namespaces. It isolates the agent's execution environment from the host system.

  • No Network Access (Allowlist only)
  • Read-Only Host Filesystem
  • Restricted Syscalls
SANDBOX CONFIG
# /etc/weaver/birdcage.toml
mode = "strict"
network = false
mounts = [
"{ src: '/project', dst: '/app', rw: true }",
"{ src: '/usr/lib', dst: '/usr/lib', rw: false }"
]
capabilities = [] # Drop all caps
AND
POLICY ENGINE
def check_file_access(path):
if "secret" in path:
return Deny("Sensitive file access")
if path.extension not in [".rs", ".py"]:
return Deny("Invalid file type")
return Allow()

Layer 2: Policy Verification

While the sandbox prevents system damage, the Policy Engine ensures architectural integrity. Before any code is written, Weaver checks the intent against defined project rules (e.g., "No raw SQL queries," "Must use Result types").

"Even if the agent CAN write to a file, the policy dictates IF it should."

Birdcage Boundaries

Filesystem Jail

The agent sees a virtualized filesystem. It can only write to the specific project directory explicitly mounted for the task.

/project (RW)
/usr/lib (RO)
/etc (Hidden)

Network Gap

By default, the network namespace is empty (loopback only). Access to package registries (crates.io, pypi) must be explicitly allowlisted via proxy.

Allow: api.UX Pilot AI.com:443
Allow: crates.io:443
Deny: *

Resource Quotas

cgroups limit CPU cycles, memory usage, and process counts to prevent fork bombs or mining attempts by rogue agents.

CPU: 2 cores
MEM: 4GB
PIDS: 50 max

Threat Model

We assume the LLM provider may be compromised, hallucinating, or malicious. Weaver is designed to operate safely even if the agent is actively trying to escape.

01

Exfiltration Prevention

Strict egress filtering prevents agents from sending your codebase to unauthorized external servers.

02

Destructive Action Mitigation

Read-only system mounts prevent `rm -rf /` or modification of critical binaries.

03

Supply Chain Injection

Dependency lockfiles are verified against policies to prevent adding malicious crates or packages.

Operational Guidance

Do

  • Run verify often
  • Audit policy files
  • Use specific mounts
  • Review diffs manually

Don't

  • Run as root
  • Disable sandbox in prod
  • Share API keys in env
  • Blindly auto-merge

"Trust, but verify inside a chroot."

Configuration Reference

weaver.toml 
# Global Security Settings
[security]
mode = "enforce" # options: enforce, audit, disabled (dev only)
max_file_size_mb = 5
allow_network = false

# Sandbox Specifics (Birdcage)
[sandbox]
runtime = "crun"
timeout_seconds = 30
mounts = [
  "./src:/app/src:rw",
  "./Cargo.toml:/app/Cargo.toml:ro"
]

# Seccomp Profile Override
[sandbox.syscalls]
default_action = "SCMP_ACT_ERRNO"
allow = [
  "read", "write", "openat", "close", "stat", "fstat", "lseek",
  "mmap", "mprotect", "munmap", "brk", "futex"
]
