COMMANDS / ACT

Controlled
Intervention.

The act command is the effector arm of the Weaver agent. It executes code modifications through a strictly sandboxed daemon, enforcing a "Double-Lock" safety mechanism that requires explicit human confirmation for high-impact changes.

Synopsis

Submits a plan or direct command to the Weaver daemon. Actions are never executed immediately; they are first staged, then proposed, and finally applied only after verification.

SYNTAX
weaver act [OPTIONS] <SUBCOMMAND>
Daemon requires socket authentication

Subcommands & Options

Command/Flag Type Description
propose Action Submit a JSONL plan for review. Returns a proposal ID.
apply Action Execute a verified proposal. Requires --id <ID>.
--dry-run Flag Simulate execution without modifying files. Returns diffs.
--sandbox-level Enum Isolation strictness: process (default), container, or vm.
--timeout Int (ms) Hard limit for execution time. Default 5000ms.
SAFETY ARCHITECTURE

The "Birdcage" Sandbox

Code execution happens in an ephemeral environment using seccomp-bpf filters to prevent unauthorized syscalls.

FIG. 4.2 - ISOLATION BOUNDARY

Violation Policy: Any attempt to access unauthorized paths (e.g., /etc/passwd, ~/.ssh) immediately kills the child process and logs a security event.

Workflow: The Proposal Cycle

STEP 1

Propose a Change

Agents cannot modify files directly. They must submit a structured plan describing the intended changes.

TERMINAL
$ cat plan.jsonl | weaver act propose
STDOUT
{
  "status": "received",
  "proposal_id": "prop_8x92mK",
  "impact_analysis": {
    "files_touched": 2,
    "risk_score": "low"
  }
}
STEP 2

Apply with Verification

Once reviewed (by human or automated policy), the proposal is applied. The daemon streams the results of each operation.

TERMINAL
$ weaver act apply --id prop_8x92mK
STREAM
// Op 1: Modify File
{
  "op": "patch",
  "file": "src/main.rs",
  "result": "success",
  "checksum": "sha256:e3b0c442..."
}
// Op 2: Run Tests
{
  "op": "exec",
  "cmd": "cargo test",
  "exit_code": 0
}
// Completion
{
  "status": "completed",
  "duration_ms": 1240
}

Common Failure Modes

ERR_SANDBOX_VIOLATION

The code attempted to access a file outside the allowed workspace scope.

Access denied: /etc/hosts
ERR_LOCK_TIMEOUT

Proposal was not approved within the configured time window.

Proposal prop_99 expired
ERR_CHECKSUM_MISMATCH

The file changed on disk between proposal and application.

Stale file handle
